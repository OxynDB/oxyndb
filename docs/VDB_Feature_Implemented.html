Install & setup

A1

One-line installer (macOS / Linux)

Working
What it does
Installs the vdb binary with one command.
How it works
deploy/install.sh detects OS (darwin/linux) and arch (arm64/amd64), downloads vdb-<os>-<arch> from the GitHub release, installs to $PREFIX/bin (sudo only if needed). On macOS it also stages vdb-linux-<arch> into $PREFIX/share/vectoradb for the VM.
How to use
curl -fsSL https://raw.githubusercontent.com/vectoradb/vectoraDB/main/deploy/install.sh | sh · env VDB_VERSION, VDB_REPO, VDB_DIST (local folder), VDB_PREFIX (default /usr/local).
How to test
No automated test. Manual: VDB_DIST=./dist VDB_PREFIX=$HOME/.local sh deploy/install.sh then vdb version.
Status & limits
Working. Does not verify the published SHA256SUMS.
Added in
c9afda7 (PR #1); URLs repointed to the vectoradb org in 0b125f9.
A2

Windows installer (install.ps1)

Partial
What it does
From a bare Windows machine to a running database with irm … | iex.
How it works
deploy/install.ps1 Invoke-Install: (1) installs WSL (wsl --install --no-distribution, elevates if needed; registers a RunOnce resume across a reboot); (2) downloads vdb-windows-amd64.exe, vdb-linux-amd64, vectoradb-docker-context.tar.gz; (3) downloads the Ubuntu noble WSL rootfs verified against Ubuntu's SHA256SUMS; (4) adds the folder to PATH; (5) runs vdb setup. Forces TLS 1.2, BOM-free ASCII.
How to use
PowerShell: irm https://raw.githubusercontent.com/vectoradb/vectoraDB/main/deploy/install.ps1 | iex · env VDB_VERSION, VDB_REPO, VDB_PREFIX, VDB_NO_SETUP, VDB_NO_ELEVATE, VDB_ROOTFS_URL.
How to test
Pester: deploy/install.Tests.ps1, deploy/windows-install.Tests.ps1 (E2E group needs VDB_TEST_E2E); windows-ci.yml checks BOM/ASCII and PS 5.1 parsing.
Status & limits
Works, but never downloads the prebuilt vectoradb-distro.tar.gz (every install takes the slower apt path) and does not verify VectoraDB's own assets against SHA256SUMS.
Added in
4fc8afb (PR #1); one-command flow 0c71da9, verified downloads d0c1f26 (PR #7); resume fix 288c431 (PR #8).
A3

vdb setup on macOS (Lima)

Working
What it does
Creates/starts a Linux VM, installs Docker + ZFS, installs the engine and starts the stack.
How it works

A9

vdb update

Partial
What it does
Installs the newest release in one command — the new engine, restarted servers, Blackbox upgrades on running branches, and vdb on the computer — without touching databases, branches, backups or settings. Before, updating meant re-running the installer, then vdb setup (which left old servers running), then vdb blackbox upgrade --all.
How it works
internal/host/host_update.go, run on the computer on every platform. (1) Downloads every file this platform needs into ~/.vectoradb/updates/<tag>/, each checked against SHA256SUMS as it streams — nothing changes unless all verify. (2) Copies the new engine into the VM / WSL distro and runs its version (wrong CPU or corrupt → stop). On macOS, asks for sudo now if /usr/local/bin isn't writable; Homebrew installs are refused. (3) vdb _update-guest stop-services, run with the new engine, stops the three servers (they must stop: start leaves running ones alone); Postgres, MinIO and branch containers keep running. (4) _update-guest install-engine writes the engine next to the installed one and renames it over (the old one is kept in ~/.vectoradb/updates/prev/vdb in the VM); if this fails the servers are restarted on the old engine. Windows also refreshes the Postgres image build context in the distro and next to vdb.exe (previous kept as .prev; only future image builds use it). (5) With the new engine: vdb up (running containers left alone; main's Blackbox re-applied), vdb ledger upgrade --all, vdb start. (6) Replaces vdb on the computer — macOS: write-and-rename (sudo if needed); Windows: the running vdb.exe is renamed to vdb.exe.old and the new one copied in — keeping the previous copy in ~/.vectoradb/updates/prev/, and refreshes the engine vdb setup would install. Then checks the versions and that the control plane answers. On Linux the host binary is the engine, so steps 2–5 run on the machine itself. Never re-imports the distro, recreates storage, changes images or rewrites data files.
How to use
vdb update (asks to confirm) · --check only reports · --yes / -y no prompt (required without a terminal) · --version vX.Y.Z a specific newer release. Going back: reinstall the older version with the installer (VDB_VERSION=…); the previous binaries are kept.
How to test
Unit: internal/host/host_update_test.go (step order with a fake VM; check only, up to date, dev build, tampered download, no terminal, stdin closed, answered no and an engine that doesn't run all change nothing; a failed install restarts the old engine and leaves the host binary alone), internal/update/update_test.go (downloads, install with the previous copy kept, Windows-style executable swap, image context replace with path-traversal refusal), cmd/vdb/update_test.go (flags). Integration: make integration-update (Lima VM, Linux path, local fake GitHub). Manual, not automated: on a Mac, vdb start shows the notice and vdb update replaces /usr/local/bin/vdb and the VM engine; on Windows, the vdb.exe swap and image context refresh.
Status & limits
Partial: the Linux path is verified end to end in the VM; the macOS and Windows paths are unit-tested and compile, but have not yet been run against a real release. The first release that contains vdb update must be installed the usual way. Checksums prove the files match the release, not who published it (no signatures). No automatic rollback: the previous binaries are kept for a manual one. Doesn't update the VM, WSL distro, Postgres or MinIO images. vdb setup's own engine download (A7) still uses /releases/latest without checksums.

Blackbox 2.0 capture (transaction, WAL position, provenance)

H10

Checkpoints & anchors

Working
What it does
Takes tamper-evidence outside the database. At intervals it records a Merkle root over the newest ledger entries — in the database and as a read-only anchor file somewhere else — so rewritten, deleted or wiped history can be proven later.
How it works
vdb.ledger_checkpoints (ledger_v2.sql) is append-only, and a trigger refuses any checkpoint that doesn't continue the last one (from_id = last to_id + 1, prev_root = last root). The engine (internal/branch/checkpoint.go) reads the new entries, refuses if their hash chain is already broken, and builds the anchor with internal/ledger/integrity.go: each leaf is sha256(0x00 ‖ recomputed row hash ‖ "|" ‖ capture hash), each node sha256(0x01 ‖ left ‖ right). It records the checkpoint, then writes ~/.vectoradb/anchors/<branch>/<to_id>.json with mode 0444, never overwriting. A scheduler in the control plane checkpoints running branches every VECTORADB_CHECKPOINT_INTERVAL (10m) or once VECTORADB_CHECKPOINT_ENTRIES (500) are waiting; VECTORADB_CHECKPOINTS=off disables it. VECTORADB_ANCHOR_DIR moves anchors (e.g. to a write-once mount); VECTORADB_ANCHOR_IMMUTABLE=1 adds chattr +i. The format is published in docs/ledger-anchor-format.md.
How to use
vdb ledger checkpoint [branch] · POST /api/branches/{name}/ledger/checkpoint · web Integrity page → Create checkpoint
How to test
Unit: internal/ledger/integrity_test.go. integration-v2 §3: anchor written read-only in the published format; no-op when nothing is new; the database refuses an out-of-sequence checkpoint; checkpoints are append-only. §3b: the scheduler anchors new entries on its own.
Status & limits
Verified in the VM (integration-v2 §3 and §3b, 14 Sep 2026). Anchors are only as trustworthy as where they're stored — the default directory is on the same host, so point VECTORADB_ANCHOR_DIR at storage the database's operators can't rewrite. Entries written since the last checkpoint are protected by the hash chain only. Cloud write-once anchor writers (S3 Object Lock etc.) are not built (commercial scope). A cloned branch inherits its parent's checkpoint rows but not its anchor files.
Added in
Blackbox 2.0 Phase 3 (feat/ledger2-phase3-checkpoints).

H15

Policy gate (warn / block)

Working
What it does
Checks every schema change against policy rules before it runs. A warn rule lets the change through and tells the client why it is risky; a block rule refuses it. Tools and agents get a machine-readable answer they can act on, defined in the published contract docs/policy-errors.md.
How it works
internal/ledger/policy.sql, installed after the 2.0 objects by EnsureLedgerV2 (every vdb start, vdb blackbox upgrade). Rules live in vdb.policy_rules (rule id, command tag, optional case-insensitive regex over the statement, warn|block, reason, hint, enabled); changes go to the append-only vdb.policy_rule_history with who made them. The event trigger vdb_policy_start fires on ddl_command_start after the guardrail vdb_guard_start (name order). Warn: an evaluation row and a NOTICE with SQLSTATE VDB02. Block: a BLOCKED Blackbox entry (risk policy) and an evaluation written through dblink so they survive the rollback, then an ERROR with VDB01; blocks win over warnings. DETAIL is one-line JSON (v, rule_id, action, command, matched, reason, hint, override, evaluation_id, blackbox_id, impact). Override: superusers and vdb_admin members may SET vdb.policy_allow = '<rule ids>'; it is recorded as an allowed evaluation and in the capture row's override_used; vdb.allow_destructive does not override policy. Fail-safe: any error while matching or recording becomes a WARNING and never stops a statement a warn rule matched; a block still refuses (with evaluation_id null). The gate ignores the client-settable vdb.v2; a superuser turns it off with ALTER EVENT TRIGGER vdb_policy_start DISABLE. Rule changes through REST need vdb_admin on that branch (IsAdmin); clients can read rules and evaluations but not write them. The existing guardrail (vdb.policy, DROP TABLE/SCHEMA, SQLSTATE 42501) is unchanged.
How to use
vdb policy · vdb policy check "ALTER TABLE orders DROP COLUMN note" (exit 1 if a rule would block) · vdb policy block drop-column · vdb policy add no-orders-drop --command "ALTER TABLE" --pattern 'orders' --block --reason "orders is shared" · vdb policy evaluations · REST GET|POST /api/branches/{n}/policies, PUT|DELETE …/policies/{rule}, POST …/policies/check, GET …/policies/evaluations · MCP policy_check · web Policies page. H17

Impact analysis

Working
What it does
Before a schema change runs, shows what it would affect: what depends on the object, which other branches have it, what the policy gate would say, and how risky it is overall — for people (vdb impact) and for agents (MCP impact, and inside every execute_change result).
How it works
Target: ledger.ParseTarget reads the statement to find the table, view, materialized view, index or sequence it changes and, where relevant, the column and kind of change (drop, drop-column, alter-column-type, rename, rename-column, truncate are destructive; alter, alter-column, create-index, grant, revoke are not). Quoted and schema-qualified names work; --object/--column name it directly. Dependents: the read-only SQL function vdb.blast_radius(target, column, depth) (internal/ledger/impact.sql, installed by EnsureLedgerV2, runs with the caller's rights and search path, so an unqualified name resolves as in the caller's own statement) walks pg_depend for normal and automatic dependencies and reports each dependent's type, identity, owning relation, depth and the view it was reached through: views and materialized views (and views on those, up to depth 5, capped at 10), constraints including foreign keys from other tables, indexes, triggers, row-level security policies, defaults, owned sequences and SQL-standard functions. For a column, only what uses that column. Every reported name is schema-qualified, and an index is reported against the table it indexes. Branches: every other running branch is checked for the object (and column) without waking suspended ones, with the branch it was cloned from (ZFS origin, btrfs parent UUID). Policy: the rules the statement would trigger (H15). Score (scoreImpact): destructive 5, otherwise 1; each dependent view, function or foreign key from another table +3, trigger or policy +2, index or other +1; deeper than checked +3; ≥10k rows +1, ≥1M +3; each other running branch with it +1 (max 5); a blocking rule +5, a warning +2. 15+ high, 5–14 medium, below low; every point is listed as a reason.
How to use
vdb impact "ALTER TABLE orders DROP COLUMN note" · vdb impact --object orders_summary --json · vdb impact "DROP TABLE orders" --branch qa · REST POST /api/branches/{n}/impact with {"sql": …} or {"object": …, "column": …} · MCP impact · SQL: SELECT vdb.blast_radius('public.orders', 'note')
How to test
Unit: internal/ledger/impact_test.go (TestSchemaImpact — read-only, capped depth, caller's rights; TestParseTarget — 27 statements; TestTargetDestructive) and internal/branch/impact_test.go (TestScoreImpact, TestBranchParentParsing — ZFS and btrfs output, TestFormatImpact). integration-v2 §8: a table's views (depth 1 and 2, via), the foreign key from another table and its index; a column's dependents only; quoted names; non-destructive changes; a missing object; a statement without a target asks for --object; a view's dependents; the depth limit; the object on a branch cloned after it existed (with its parent) and not on one without it; the policy verdict in the score; REST and MCP agree with the CLI; execute_change includes the impact.
Status & limits
Verified in the VM (integration-v2 §8, 15 Sep 2026; existing suite 28 / 28). The target is read from the statement text: one object per statement (the first of a multi-object DROP), and statements on functions, types, schemas or whole-schema grants aren't recognised — name the object with --object. H18

Blackbox diff between branches

Working
What it does
Shows which schema changes distinguish two branches: where they split, what was changed only on each since, and which objects were changed on both (likely conflicts). Diff only — nothing is merged or changed.
How it works
branch.DiffLedgers (internal/branch/diff.go) reads both branches' Blackbox histories in id order (starting a suspended branch first, as other Blackbox commands do). A branch is a copy-on-write clone, so it begins with its parent's history entry for entry; the fork point is the longest run of entries with the same id and the same recomputed hash. Everything after it is listed for each side (id, time, command, object, status, actor). Objects changed on both sides are listed with their entry ids; BLOCKED entries don't count, since those changes never happened. Each branch's parent is read from the storage layer.
How to use

Status & limits
Verified in the VM (integration-v2 §8, 15 Sep 2026; existing suite 28 / 28). Branches that weren't cloned from each other (e.g. two imports) have no shared history, so everything shows on both sides.
