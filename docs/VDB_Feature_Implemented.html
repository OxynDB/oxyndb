Area A

Install & setup

A1

One-line installer (macOS / Linux)

Working
What it does
Installs the vdb binary with one command.
How it works
deploy/install.sh detects OS (darwin/linux) and arch (arm64/amd64), downloads vdb-<os>-<arch> from the GitHub release, installs to $PREFIX/bin (sudo only if needed). On macOS it also stages vdb-linux-<arch> into $PREFIX/share/vectoradb for the VM.
How to use
curl -fsSL https://raw.githubusercontent.com/vectoradb/vectoraDB/main/deploy/install.sh | sh · env VDB_VERSION, VDB_REPO, VDB_DIST (local folder), VDB_PREFIX (default /usr/local).
How to test
No automated test. Manual: VDB_DIST=./dist VDB_PREFIX=$HOME/.local sh deploy/install.sh then vdb version.
Status & limits
Working. Does not verify the published SHA256SUMS.
Added in
c9afda7 (PR #1); URLs repointed to the vectoradb org in 0b125f9.
A2

Windows installer (install.ps1)

Partial
What it does
From a bare Windows machine to a running database with irm … | iex.
How it works
deploy/install.ps1 Invoke-Install: (1) installs WSL (wsl --install --no-distribution, elevates if needed; registers a RunOnce resume across a reboot); (2) downloads vdb-windows-amd64.exe, vdb-linux-amd64, vectoradb-docker-context.tar.gz; (3) downloads the Ubuntu noble WSL rootfs verified against Ubuntu's SHA256SUMS; (4) adds the folder to PATH; (5) runs vdb setup. Forces TLS 1.2, BOM-free ASCII.
How to use
PowerShell: irm https://raw.githubusercontent.com/vectoradb/vectoraDB/main/deploy/install.ps1 | iex · env VDB_VERSION, VDB_REPO, VDB_PREFIX, VDB_NO_SETUP, VDB_NO_ELEVATE, VDB_ROOTFS_URL.
How to test
Pester: deploy/install.Tests.ps1, deploy/windows-install.Tests.ps1 (E2E group needs VDB_TEST_E2E); windows-ci.yml checks BOM/ASCII and PS 5.1 parsing.
Status & limits
Works, but never downloads the prebuilt vectoradb-distro.tar.gz (every install takes the slower apt path) and does not verify VectoraDB's own assets against SHA256SUMS.
Added in
4fc8afb (PR #1); one-command flow 0c71da9, verified downloads d0c1f26 (PR #7); resume fix 288c431 (PR #8).

C5

Scale-to-zero & wake on connect

Working
What it does
Idle branches stop automatically; the next connection wakes them.
How it works
Gateway reaper (proxy.go) polls every idle/3 (5–30s) and suspends a branch only when idle ≥ threshold and ActiveConnections = 0. On connect, EnsureRunning routes, recreates or resumes the container and re-enables the guard (reconcileGuard).
How to use
vdb gateway --idle 2m (default via vdb start); --idle 0 disables.
How to test

H10

Checkpoints & anchors

Working
What it does
Takes tamper-evidence outside the database. At intervals it records a Merkle root over the newest ledger entries — in the database and as a read-only anchor file somewhere else — so rewritten, deleted or wiped history can be proven later.
How it works
vdb.ledger_checkpoints (ledger_v2.sql) is append-only, and a trigger refuses any checkpoint that doesn't continue the last one (from_id = last to_id + 1, prev_root = last root). The engine (internal/branch/checkpoint.go) reads the new entries, refuses if their hash chain is already broken, and builds the anchor with internal/ledger/integrity.go: each leaf is sha256(0x00 ‖ recomputed row hash ‖ "|" ‖ capture hash), each node sha256(0x01 ‖ left ‖ right). It records the checkpoint, then writes ~/.vectoradb/anchors/<branch>/<to_id>.json with mode 0444, never overwriting. A scheduler in the control plane checkpoints running branches every VECTORADB_CHECKPOINT_INTERVAL (10m) or once VECTORADB_CHECKPOINT_ENTRIES (500) are waiting; VECTORADB_CHECKPOINTS=off disables it. VECTORADB_ANCHOR_DIR moves anchors (e.g. to a write-once mount); VECTORADB_ANCHOR_IMMUTABLE=1 adds chattr +i. The format is published in docs/ledger-anchor-format.md.
How to use
vdb ledger checkpoint [branch] · POST /api/branches/{name}/ledger/checkpoint · web Integrity page → Create checkpoint
How to test
Unit: internal/ledger/integrity_test.go. integration-v2 §3: anchor written read-only in the published format; no-op when nothing is new; the database refuses an out-of-sequence checkpoint; checkpoints are append-only. §3b: the scheduler anchors new entries on its own.
Status & limits
Verified in the VM (integration-v2 §3 and §3b, 14 Sep 2026). Anchors are only as trustworthy as where they're stored — the default directory is on the same host, so point VECTORADB_ANCHOR_DIR at storage the database's operators can't rewrite. Entries written since the last checkpoint are protected by the hash chain only. Cloud write-once anchor writers (S3 Object Lock etc.) are not built (commercial scope). A cloned branch inherits its parent's checkpoint rows but not its anchor files.
Added in
Blackbox 2.0 Phase 3 (feat/ledger2-phase3-checkpoints).

H13

Branch from just before a Blackbox entry

Working
What it does
Creates a new branch holding main exactly as it was the moment before a chosen schema change — to inspect what things looked like, or to recover from a bad change — without touching main.
How it works
BranchBeforeEntry (internal/branch/branch_before.go) reads the entry and its captured transaction id and WAL position (H9) from the current primary, and refuses BLOCKED entries (the change never happened), sources other than main (only the primary archives WAL) and names already in use. It switches main to a new WAL segment and waits for the archiver, so the change's commit is in object storage. It lists base backups (wal-g backup-list --json --detail in a throwaway container) and picks the newest backup of the same database (system identifier) that finished before the change — by WAL position, or by time for entries without capture. It creates empty storage for the new branch and runs the stock image with an embedded script (internal/branch/restore_before.sh, passed with bash -c, so the published image needs no new file): backup-fetch of that backup, recovery_target_xid (or recovery_target_time) with recovery_target_inclusive = off, then promote. Once promoted it checks the entry is absent, clears the recovery settings (ALTER SYSTEM RESET), restarts the data directory as an ordinary branch container and re-enables the guardrail. Any failure removes the partial branch. One runs at a time.
How to use
Find the entry id with vdb ledger entries [--limit N] (REST GET /api/branches/main/ledger/entries, MCP ledger_entries; the existing ledger views don't show ids and are unchanged), then vdb ledger branch-before 612 [--as fix-orders] (default name main-before-612) · REST POST /api/branches/main/ledger/612/branch with optional {"name": "…"} (201; 400 invalid or BLOCKED, 404 no such entry, 409 name taken, 422 no usable base backup) · MCP branch_before_change · web Integrity page → "Branch from before a change". Connect through the gateway like any branch; remove it with vdb branch delete.
How to test
Unit: internal/branch/branch_before_test.go and ledger_entries_test.go (entry listing, entry parsing, xid/time targets, backup-list parsing, base-backup choice incl. another database's backups, WAL-archive check, names, the embedded script). integration-v2 §4: the entry id is listed by CLI, REST and MCP; by transaction id via the CLI — rows written before the change (even after the backup) are present, the change and later changes are not, the ledger stops before the entry, no recovery settings left, reachable through the gateway with the guardrail active, main untouched and its integrity result unchanged; by timestamp via MCP for an entry without capture; via REST; refusals for an existing name, a BLOCKED entry, an unknown entry, a non-main source and a bad id, with nothing left behind.
Status & limits
Verified in the VM (integration-v2 §4, 14 Sep 2026: by transaction id, by timestamp, via CLI, REST and MCP). Takes minutes, not seconds (base backup fetch plus WAL replay), and the REST call waits for it. Needs a base backup that finished before the change (vdb backup create; schedule backups to make older changes reachable). It excludes the change's whole transaction, so other statements in the same transaction are excluded too. Entries recorded before Blackbox 2.0 capture use their timestamp, which also excludes anything that committed after the change started. Only main can be the source; after an HA failover the promoted standby doesn't archive WAL, so later changes can't be branched before. The new branch keeps main's checkpoint rows up to that point but not its anchor files, so vdb ledger integrity on it notes the difference.

H15

Policy gate (warn / block)

Working
What it does
Checks every schema change against policy rules before it runs. A warn rule lets the change through and tells the client why it is risky; a block rule refuses it. Tools and agents get a machine-readable answer they can act on, defined in the published contract docs/policy-errors.md.
How it works
internal/ledger/policy.sql, installed after the 2.0 objects by EnsureLedgerV2 (every vdb start, vdb blackbox upgrade). Rules live in vdb.policy_rules (rule id, command tag, optional case-insensitive regex over the statement, warn|block, reason, hint, enabled); changes go to the append-only vdb.policy_rule_history with who made them. The event trigger vdb_policy_start fires on ddl_command_start after the guardrail vdb_guard_start (name order). Warn: an evaluation row and a NOTICE with SQLSTATE VDB02. Block: a BLOCKED Blackbox entry (risk policy) and an evaluation written through dblink so they survive the rollback, then an ERROR with VDB01; blocks win over warnings. DETAIL is one-line JSON (v, rule_id, action, command, matched, reason, hint, override, evaluation_id, blackbox_id, impact). Override: superusers and vdb_admin members may SET vdb.policy_allow = '<rule ids>'; it is recorded as an allowed evaluation and in the capture row's override_used; vdb.allow_destructive does not override policy. Fail-safe: any error while matching or recording becomes a WARNING and never stops a statement a warn rule matched; a block still refuses (with evaluation_id null). The gate ignores the client-settable vdb.v2; a superuser turns it off with ALTER EVENT TRIGGER vdb_policy_start DISABLE. Rule changes through REST need vdb_admin on that branch (IsAdmin); clients can read rules and evaluations but not write them. The existing guardrail (vdb.policy, DROP TABLE/SCHEMA, SQLSTATE 42501) is unchanged.
How to use
vdb policy · vdb policy check "ALTER TABLE orders DROP COLUMN note" (exit 1 if a rule would block) · vdb policy block drop-column · vdb policy add no-orders-drop --command "ALTER TABLE" --pattern 'orders' --block --reason "orders is shared" · vdb policy evaluations · REST GET|POST /api/branches/{n}/policies, PUT|DELETE …/policies/{rule}, POST …/policies/check, GET …/policies/evaluations · MCP policy_check · web Policies page. In an application: catch SQLSTATE VDB01 and parse the error's DETAIL as JSON.
How to test
Unit: internal/ledger/policy_test.go (TestSchemaPolicy — both SQLSTATEs, fires after the guardrail, built-ins ship as warn, ignores vdb.v2, touches no existing object; TestParsePolicyDetail; TestPolicyContractExample — the contract's own example parses; TestCommandTag; TestValidRuleID) and internal/branch/policy_test.go (validation, rule SQL quoting, error messages, formatting). integration-v2 §6: warn (runs, VDB02, contract JSON, evaluation) for all four built-ins; block (VDB01, statement didn't run, JSON with ids, BLOCKED entry and evaluation survive the rollback, HINT names the override); non-admin override, vdb.v2=off and vdb.allow_destructive don't bypass; admin override runs and is recorded; REST list / 200 / 403 / 404 / 409 / check / evaluations; CLI check and exit code; MCP policy_check; clients can't write rules; fail-safe; kill switch; custom and disabled rules; rule history; invalid pattern; built-in can't be removed; append-only evaluations; guardrail error unchanged; reinstall keeps rule changes; hash chain still verifies.
Status & limits
Verified in the VM (integration-v2 §6, 14 Sep 2026; existing suite 28 / 28). Patterns match the whole query text the client sent, so a multi-statement string is matched as a whole and text inside comments or string literals can match. vdb policy check guesses the command tag from the statement's first words; the gate itself uses the real tag. TRUNCATE is not covered (it doesn't fire DDL event triggers). Imports and pipelines run through the gate too (with the built-in warn rules that only adds notices). Rules are per branch; new branches copy main's. The impact field is always null until impact analysis (Phase 7).

Blackbox 2.0 Phase 5 (feat/blackbox-phase5-policy).

Configure an MCP client to launch command vdb with args ["mcp"].

Status & limits
run_sql runs as the non-superuser vdbclient, attributed to mcp; VECTORADB_MCP_SUPERUSER=1 restores the superuser. list_branches no longer shows passwords. No auth (local privileges). No client config snippet in docs.

Known issues

Found while building this inventory. Recorded, not fixed — each fix changes existing behaviour and needs explicit approval. Struck-through items have been fixed.

  1. PITR restore broken on fresh installs (hardcoded minioadmin) — fixed in Phase 1. (D3, H7)
  2. Destructive-DDL override ungated — fixed in Phase 1 (superusers and vdb_admin only). Use of the override is now recorded (H9). (H4, H8)
  3. Agents and MCP run as superuser — fixed in Phase 1 (own agent-<id> role; MCP as vdbclient). (K5, K6, H3)
  4. Integration §1 and §5 call http:// endpoints that now serve TLS — fixed in 13734a7.
  5. Integration "bad key" and "append-only" checks gave false failures — fixed (test-only; both protections confirmed working in the VM).
  6. vdb branch suspend main stops the primary and the gateway won't wake it. (C3)
  7. vdb ha enable after a failover deletes the live primary (vec-standby); post-failover ha disable routes main to a stopped container. (D4)
  8. backup/restore always target vec-main, even after a failover; PITR always fetches the LATEST base backup. Branching from before a ledger entry (H13) picks the right base backup and reads the ledger from the current primary, but base backups are still only taken from vec-main. (D2, D3, H13)
  9. Ledger verify can't detect deletion of the newest rows or a wiped table — addressed in Phase 3: checkpoint anchors kept outside the database catch it (H10–H12). Entries written since the last checkpoint are still only chain-checked. (H2)
  10. The 2.0 capture kill switch vdb.v2 = 'off' could be set by any client for its own session, skipping its capture rows — fixed: it is now honoured only database-wide or in a superuser's session. (H9)
  11. Policy patterns match the whole query text a client sent (all statements of a multi-statement string, comments and literals included). (H15)
  12. vdb ledger revert --to doesn't revert a branch. (H7)
  13. README documents vdb branch diff (doesn't exist) and ledger UI filters by table/risk (not in the UI). (L5)
  14. OpenAPI spec disagrees with the code (import fields, status codes, missing params/routes). (K2)
  15. .sql imports don't stop on error; JSON array imports stop silently at the first bad element; web Import mentions SQLite (no loader). (I5, I6, I12)
  16. Continuous-import cutover is CLI-only. (I8)
  17. Agent cap and TTL reaper only count running containers; agent DSN only reachable inside the VM. (K5)
  18. OAuth defaults point at http://localhost:8080 / http://localhost:5173. (G5)
  19. vdb vm is listed as a command but not implemented. (B1)
  20. Windows installer never downloads the prebuilt distro; its preloaded image tag doesn't match the engine's image name; setup summary omits the API key. (A2, A4, M5)
  21. Web Guide/Docs pages are stale in places. (L7)
  22. Storage quotas are ZFS-only and per-branch caps are opt-in. (C6)
  23. The Postgres image has no pgvector. (M6)
